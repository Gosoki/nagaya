# 長屋 nagaya — 合租记账系统 任务书

> 状态：**M1 + M2 已完成并自测通过**（2026-09-21）。决策 D1–D18。
> 测试：后端 pytest 103 · 前端 vitest 27 · 手机 E2E 13（WebKit 375px）。
> 下一步 M3（光熱費套餐 / 复制上月 / 模板 / 左滑删除 / 审计日志页 / 备份 / 部署）。
> 项目名 **`nagaya`**（長屋＝江户时代庶民合住的联排出租屋，「合租」的老祖宗）。
> 目标用户：日本，3 人合租（近期可能变 4 人），手机为主、电脑为辅。

## 0. 一句话

**一个自托管的合租账本：记谁付了什么、按各自的分摊规则算出谁欠谁多少、月底出一张能直接贴进 LINE 的账单、结清后归零、没结清就挂账结转。**

## 2. 需求 → 设计判断

| 你的需求 | 设计判断 |
|---|---|
| 分摊比例 1:1:1 / 1:1:0 / 2:1:0 | 权重（weight）模型。**权重 0 ＝ 不参与**，不是特例，和 1:1:0 同一套代码 |
| 比例之外还能「多负担多少」（a−1000 b+500） | **调整额（adjustment）**：每人一个可正可负的固定日元数，和比例叠加。语义按 **D1** |
| 方便编辑 | 所有账目可改可删；**但已关账的月份锁定**，改要先解锁并留痕 |
| 快速生成新账单 | 三招：① 一键**复制上月** ② **模板**（家賃固定额）③ **光熱費套餐**（电/煤/水/网一屏录入） |
| 不只房租水电煤，还有网费和日常公共支出 | 分类表自由增删，存数据库、面板可改，不写死在代码里 |
| 水费两月一收 | 按 **D2** 现金制；账目带「计费期间」字段仅用于账单上标注「含 7–8 月水费」 |
| 出账单 | 月度账单页 + 一键复制成文本（LINE 贴）/ PNG / CSV |
| 清账了就平账 | 结算（settlement）也是一条账目：A→B ¥X，记完余额归零 |
| 可以暂时赊账 | **不需要额外机制**：余额本来就是累计的。少付部分自动结转，账单标「上月结转 −¥X」 |
| 集体收入（返现之类） | 收入＝金额取负的支出。**统一成一张表**，不搞两套逻辑 |
| 提前入账（D3） | 任意日期都能记一笔转账；账单自动抵扣，显示「已预付 ¥X，本月还需 ¥Y」 |
| 以后第 4 个人 | 成员有加入日/退出日；**每笔账的分摊结果是落库快照**，新人加入不改写历史账 |

## 3. 参考调研：抄什么、不抄什么

| 项目 | 技术 | 值得抄 | 不抄 |
|---|---|---|---|
| **Splitwise**（商业） | — | 分摊四模式（均分/百分比/份额/**调整额**）、simplify debts（最少转账）、余额恒等式 | 广告、云端、多群组 |
| **Spliit** ([spliit-app/spliit](https://github.com/spliit-app/spliit)) | Next.js + Prisma + Postgres | PWA（手机加桌面图标）、「全选/全不选参与人」、报销账目、收据附件 | 整套 JS 栈太重 |
| **IHateMoney** ([spiral-project/ihatemoney](https://github.com/spiral-project/ihatemoney)) | Flask + SQLite | **成员带权重**、**成员停用但保留历史**、结算方案、极简思路 | 已进维护模式；它的权重是成员级全局权重，我们要**每笔账独立权重** |
| **Cospend** ([julien-nc/cospend-nc](https://github.com/julien-nc/cospend-nc)) | Nextcloud app | **周期性账单**、**从结算方案自动生成报销账目**、账目回收站 | 绑 Nextcloud |

**共识做法（三家都这么干，我们照做）：**
1. 金额**一律整数最小单位**存（日元就是 `int`，**禁止 float**）
2. 分摊余数用**最大余数法（Hamilton）**，保证各人份额**加起来严格等于总额**
3. 余额 = Σ我付的 − Σ我该担的；**全体余额之和恒等于 0**（最强自检）
4. 结清 = 记一笔转账，不是「删除历史」

**我们比它们多的**：调整额 ＋ 比例叠加（Splitwise 的调整额只能配均分）、光熱費打包录入、两月一次的水费、中日双语。

## 4. 算法（最要紧的部分）

### 4.1 分摊计算：两种模式

**模式一：固定金额（exact）—— 家賃走这个（D12）**

每人直接手填一个整数日元：

```
家賃 ¥120,000 →  A 45,000 / B 40,000 / C 35,000
校验 Σ == amount，不等就在界面上红字显示差额 ±¥X，并给一键
「把差额摊给全部人 / 摊给某个人」，不平不许存
```
> 固定金额模式下没有「调整额」——数字就在眼前，直接改就是了。

**模式二：比例 ＋ 调整额（ratio）—— 水电煤网、日用品走这个**

输入：`amount`（整数日元，可负）、`weights`（{成员: 权重}）、`adjustments`（{成员: 整数日元，可正可负}）

```
1. base = amount − Σ adjustments
2. base 按 weights 分配：
     raw_i   = base × w_i / Σw
     share_i = floor(raw_i)
     余数 r  = base − Σ share_i
     把 r 个 1 円依次给「小数部分最大」的人（平局规则见 §4.3）
3. share_i += adjustment_i
4. 断言 Σ share_i == amount，不成立直接拒绝落库
```

全程 `Decimal` 或纯整数运算，**不出现 float**。

### 4.2 调整额语义（D1 已定：自动配平）

电费 ¥9,000，`a:b:c = 1:1:1`，`a−1000`，`b+500`：

```
base = 9000 − (−1000 + 500) = 9500
9500 按 1:1:1 → 3167 / 3167 / 3166
加调整：a = 3167−1000 = 2167，b = 3167+500 = 3667，c = 3166
合计 9000 ✔
```

含义：**a 比按比例应担的少付 1000，b 多付 500，差额三个人共同吸收。**
永远自动配平，不需要指定「兜底的人」。

> 备选方案 B（净差全压给某个指定人）已否决：多一个每笔都要选的字段，
> 而且三个人的场景里「差额大家共同吸收」本来就是更常见的意图。

### 4.3 余数 1 円给谁

最大余数法平局时（1:1:1 分 ¥10,000 三人小数部分相同）要有确定规则：
- **(a) 给付款人**：最简单，付钱的人吃/占那 1 円 ← **默认**
- (b) 按成员固定顺序
- (c) 逐月轮转（entry 序号取模）

做成设置项（数据库里，面板可改），默认 (a)。**不写死在代码里**。

### 4.4 跨月账单（D2 已定：现金制）

水费 ¥12,000 覆盖 7–8 月、9 月收到账单 → **全额记在 9 月，7 月和 8 月的水费就是 0**。

- `entry.period_start / period_end` 只用于**账单上标注**「含 7–8 月水费」，不参与任何计算
- 不拆分、不回改已关账的月份
- 如果期间内正好有人搬进/搬出，系统**弹提示**「此期间成员有变动，请确认分摊比例」，由你手动调权重——不自动按天算

> 副作用：月度金额会有大小月（有水费的月份贵 ¥12,000）。
> 统计页会提供「近 6 个月均值」这条线，避免被单月数字误导。

### 4.5 最少转账方案（结算）

余额算出来后贪心配对：最大债权人 ↔ 最大债务人，取较小额结一笔，重复到全为 0。
n 个人**最多 n−1 笔**（3 人最多 2 笔）。

> 副作用：会出现「原本没跟你有账的人要给你转钱」。Splitwise 也一样。
> 只有 3–4 个室友，**默认开启**；设置里留「按原始债权结算」开关。

### 4.6 账单怎么切（D23 / D24，**账期机制已整体删除**）

原来按自然月划账期，带出来一长串问题：起算日设置、月份边界、「这笔落进了哪一期」、
改起算日导致账期重叠（能把接口打成 500）、关账/解锁。**那些问题全是日历边界自己造出来的。**

现在：

```
   记账、填固定费……         你点「出账单」          再记的账
   ├──── 当前草稿账单 ────┤  划线 + 冻结快照  ├──── 下一张草稿 ────
```

- 没出账的账目（`entry.statement_id IS NULL`）合起来就是**当前这张草稿账单**
- 点「出账单」＝ 把这一刻之前的全部归到一张 `Statement` 上，冻结 `snapshot_json`
- 之后再记的账自动进下一张。没有日历，没有起算日

**不锁定历史（D24）。** 余额是全局累计的：事后改一笔已出账的账，差额会原样出现在
下一张的「上期结转」里，**钱不会算错**（有测试钉着）。关账那道门保护不了钱，
却偏偏在最该补录的时候拦人——「想起来漏了煤气费，进去一填，该期已关账」。

所以改成**标记**而不是**锁定**：那张账单出完之后被改过的话，自己说出来——
「这张出账后被改过 1 处：当初 ¥9,000，现在 ¥13,000」。快照留着举证，
下一张的「上期结转」也就解释得清了。

**已出账单的转账方案用冻结的那份。** 每人的应担/已垫付照实时算（改了就要看得见），
但「谁给谁多少」一律读 `snapshot_json` —— 那是真发到群里、大家照着转的钱。
方案要是跟着重算，按下标对位的「已完成」勾就会对到别的行上去。

举个完整的例子：一笔 30,000 出账，b、c 各转了 10,000 给 a；事后发现其实只有
18,000。那张单子的方案和勾全不动，下一张草稿上直接出现「a 该还 b、c 各 4,000」。
**多付的钱就是这样在下个账单里自己回来的**，不需要任何锁。

### 4.7 比例从哪来、改了什么时候生效（D12）

比例**没有一处是写死的**，分三层，越往下优先级越高：

| 层 | 在哪改 | 例子 |
|---|---|---|
| 1. 全局默认 | 设置页 | `1:1:1` |
| 2. 分类/模板默认 | 分类管理页，每个分类一个输入框 | **家賃＝固定金额 45000/40000/35000**、ガス `1:1:0` |
| 3. 单笔账 | 记账时展开「改分摊」 | 这个月 B 出差，`1:0:1` ＋ 调整额 |

每一层都能选「固定金额」或「比例」，两种模式随便混（家賃固定金额、水电走比例）。

**生效边界（这条很重要，别搞错）**：
- 改第 1、2 层 → **只影响之后新建的账**。历史账一个数字都不动（§5 的快照设计）
- 想改已经记过的某一笔 → **直接编辑那笔账**，保存时立刻重算这一笔（该期未关账的话）
- **不存在**「改了默认值，上个月账单跟着变」——那是账本最忌讳的事

> **你的原话**：「以前的不要动了，就从此往后」——就是这个设计。
> 所以「这个月起房租每人交多少变了」的操作是两步：改模板里的固定金额 → 把本月那笔房租编辑一下
> （或删了用模板重生成）。多一步，但每一步的结果都可预测、可解释给室友听。

## 5. 数据模型

SQLite（WAL）。**设计阶段用 `create_all`**（D18）——表结构还在改，每次生成迁移纯属添乱；
Alembic 的配置已经搭好（env.py、`import sqlmodel` 模板坑、SQLite 必需的 `render_as_batch`），
**等 schema 稳下来、准备录真实账目之前**跑一次 autogenerate 生成第一版。

```
member        成员
  id, name, display_name, color, display_order
  joined_on, left_on(可空)        -- 退出的人不删，保留历史
  is_active(派生), password_hash, lang(zh|ja), created_at

category      分类（房租/电/煤/水/网/日用品/其他，可增删改）
  id, name, icon, default_weights_json(可空), display_order, archived

entry         一笔账（支出/收入/转账 三合一）
  id, kind: expense | income | settlement
  date, title, amount_jpy(int, 收入为负)
  category_id(可空), payer_id(付款人/收款人；settlement 时＝转出人)
  to_member_id(仅 settlement：转入人)
  period_start / period_end (可空，仅用于账单标注)
  bundle_id(可空，光熱費套餐用)
  split_rule_json         -- 原始规则，为了「编辑时能还原界面」
  note, receipt_path(可空)
  created_by, created_at, updated_at, version(乐观锁), deleted_at(软删)

entry_share   分摊快照（entry 的子表）
  entry_id, member_id, amount_jpy(int, 可负)
  -- 唯一约束 (entry_id, member_id)；Σ amount_jpy == entry.amount_jpy 由应用保证

bundle        光熱費套餐（一次录入多项）
  id, month, title            -- 「2026年9月 水道光熱費」

template      模板
  id, name, kind, category_id, payer_default_id, split_rule_json,
  amount_default(可空，家賃这种固定额), items_json(套餐模板用)

period        账期（起算日可自定义，见 §4.6）
  id, label('2026-10期'), start_date, end_date
  status: open | closed, closed_at, closed_by
  snapshot_json               -- 关账时冻结的余额/成员/明细，保证账单可原样重现
  -- 约束：期间不重叠、不留空隙

setting       key-value 配置（面板可改，中日文说明）
  -- period_start_day(账期起算日,默认1) / settle_due_day(结算日,次月15或25)
  -- default_payer_id(默认垫付人,D5)
  -- remainder_to(余数归属) / simplify_debts(是否最少转账) / backup_path
audit_log     who / when / 对哪条 entry / 做了什么 / 改前改后
```

**为什么 `entry_share` 要独立存而不是现算**：
第 4 个人搬进来、某人改了默认比例、分类被删——历史账单必须纹丝不动。这是整个设计里最重要的一条。

**为什么支出/收入/转账共用一张表**：
余额公式只有一条，报表只查一张表，不会出现「收入表忘了减」这种 bug。
转账也套进同一条公式：`payer` 是**交钱的人**，`entry_share` 整笔记在**收钱的人**头上。

### 5.1 实现期补定的规则

任务书原本没写死、但写代码时必须有个答案的地方：

1. **`entry.period_id` 显式存**，不靠日期现算。因为「10/15 记的转账算进 9 月期」
   这条规则光看日期推不出来。支出/收入按发生日归期；**转账挂到最早的未关账账期**
   （＝你还的就是那一期的账）。字段可改，需要时能手动挪。
2. **往已关账的账期记账 → 拒绝**，返回 `period_closed`。钱悄悄挪进已经出过账单的
   月份，是账本最忌讳的事。
3. **金额符号强约束**：支出 > 0、收入 < 0、转账 > 0，0 一律拒绝。
   **退款/返现一律记成「收入」**，不允许用负数支出 —— 否则同一件事两种记法，
   算出来一样但报表对不上，「收入」这个类型也就形同虚设。
4. **离线草稿只在「连不上服务器」时存**（D15）。像「金额方向不对」「账期已关账」
   这类是服务器**明确拒绝**，存成草稿只会让人以后反复补交同一笔注定失败的账。
5. **关账允许带着未结清的余额**。那就是赊账，差额自动以「上期结转」出现在下一张
   账单上 —— 不是非要结清才准关账。

## 6. 功能清单

### F1 记一笔（核心，要快）
**PWA 打开的默认页就是这一屏**（D16）——启动即光标就位。

手机上 **3 步录完**：金额（大字号，唤系统数字键盘）→ 分类（大色块网格，一点即选）→ 保存。
标题选填（D9：「日用品」这种粗放写法就够，**不做商品明细子表**）。
付款人/分摊**默认折叠**，常见场景不展开就能存。操作按钮全在拇指区（§7.4）。

**「保存并继续」模式**（D9）：存完不跳转，焦点自动回到金额框，超市小票一次性录完一串。

**离线草稿**（D15）：没网也能填完，存 `localStorage`；回到有网时页面顶部横幅
「有 1 笔未提交」点一下补交。**不做后台自动同步**，避免「以为存上了其实没有」。
付款人默认＝**设置里的「默认垫付人」**（D5）；分摊规则默认＝**该分类上次用的规则**。
展开才看到「改分摊」：权重快选（`1:1:1` / `1:1:0` / `2:1:0` 芯片按钮）＋ 每人调整额输入框 ＋ **实时显示每人最终金额和合计校验**。
> 验收：常见场景（我垫了日用品，三人平分）**不展开任何高级选项就能存**。

### F2 分摊引擎
§4.1 算法 ＋ 属性测试（随机金额/权重/调整额跑 1000 组，断言恒等式成立）。

### F3 固定费一屏录完（D19〜D22，**已实现**）

家賃/電気/ガス/水道/ネット 这几项一个月才碰一次，却在日常记账那屏占了五个按钮。
所以把它们摘出来单成一屏（`/monthly`），日常网格只留日用品/食費/その他。

**入口有两处**：日常记账那屏的「本期固定费」，和账单页顶部内嵌的同一块。
账单来了随时填，不必等到出账单 —— 出账单只是「划一条线，把这一刻之前的都算进来」。

一屏长这样：每项一行，金额框 + 可展开的分摊/计费期间。
- 每项可**单独设分摊规则**（网费 1:1:1，但某人不用煤气就 1:1:0）
- **留空＝跳过**（水费那个月没有就不填，按 D2 这月就是 0）
- 各项可填计费期间（水费填 7/1–8/31，仅用于账单标注，且只有**跨期**的才会出现在账单上）
- 底部可以自己加一项：打个名字就建好了，下个月自动出现

**两条要命的约束（D21 / 归期）**：

1. **上次的金额只作灰色 placeholder，不是 value。**
   账本里预填的数字很危险 —— 长得跟亲手填的一模一样，某个月忘了改就带着上月的
   电费把账单发出去了，谁都看不出来。不动它就等于没录，这个月该项就是 0。
2. **记入日必须落在这张账单自己的期间内。**
   归期只看 `entry.date`。在 10/10 填 9 月账单时若用「今天」，那笔家賃会落进
   10 月期 —— 9 月账单上凭空少一笔且零报错。后端 `default_date_for()` 负责
   （今天在期内就用今天，否则用期末），界面上明写「算进哪一期」。

### F4 快速生成新账单
- **复制上月**：把上月全部 entry 复制到本月，日期顺延，金额沿用，进「批量编辑」页一屏改数字
- **模板**：家賃这种固定额一键生成
- （可选）**自动生成**：每月 1 号自动挂家賃——参考 Cospend 的周期账单，**建议先不做**

### F5 余额看板（第二个 tab，按 D5 排版）
既然钱主要从一个人卡上出，首页就以垫付人为主视角：

```

   ┌────────────────────┐

```
（如果哪天变成互相都有账，自动退回「每人一张卡」的通用排版。）

### F6 出账单 + 结算 + 赊账
月度账单页：

```
【2026年9月 家计账单】  合计 ¥150,400   ※未结清
                          （设了结算日就显示「10/25 前结清」）
（含 7–8 月水费 ¥12,000 · 含 10月分 家賃）

A  应担 ¥45,000＋… / 已垫付 ¥150,400            → 应收 ¥100,400
B  应担 ¥50,200      / 已预付 ¥30,000            → 应付 ¥20,200
C  应担 ¥55,200      /                           → 应付 ¥55,200
（家賃部分按固定金额 45,000/40,000/35,000，水电日用品按 1:1:1）
                                （含上月结转 −¥2,000）

▸ 转账方案（2 笔）
   B → A ¥11,434
   C → A ¥30,633
```

- **一键复制文本**（直接贴 LINE）/ 导出 PNG / CSV
- 每笔转账旁边一个 **[已完成]** 按钮（只有当事双方看得到）→ 生成 settlement entry → 余额归零
- 结算方式默认「现金」（D11），账单文本里**不附**收款账号/PayPay ID；方式做成可编辑列表，以后改用 PayPay 加一行就行
- **赊账**：金额可改小（「B 这个月先给 20,000」），差额自动结转，下月账单显示「上月结转」
- **关账**：全部结清或你手动确认后把该月 `closed`，明细锁定；解锁需确认并写 audit_log

### F7 提前入账（D3）
**任意日期都能记一笔转账**（A→B ¥30,000，备注「10 月家賃先给」），不必等月底结算。
效果：转出人余额变正（变成债权人），月底出账单时**自动抵扣**，账单上显示「已预付 ¥30,000 → 本月还需 ¥11,434」。

> **公共钱包的升级路径（MVP 不做，但路留好）**：
> 将来真要「每人每月先交 ¥X 到公共账户」，做法是把钱包建模成**一个特殊成员**
> （`member.kind = pot`，不参与分摊）——交钱＝转账给 pot，公共支出的 payer＝pot。
> **零新表，加一列 + 一段 UI 就能上。**
> 所以 MVP 阶段唯一要守住的纪律是：代码里不要假设「成员数 ＝ 住的人数」。

### F8 集体收入
记一笔时切「收入」：返现、押金返还、卖旧家具、共同消费的 point 返还。分摊规则完全复用（谁受益、按什么比例）。

## 7. 技术栈（v3：按 D14「手机 70%」重定）

### 7.1 为什么推翻了原来的 NiceGUI 方案

原方案选 NiceGUI 的理由是「和 Auto-rss2qb 同栈、最熟、单进程」——这些理由现在依然成立，
只是被「**手机占 70%**」这个约束压倒了。

问题不在长相（NiceGUI 底层就是 Quasar，移动端组件本来就没问题），**在架构**：
NiceGUI 是服务端持状态 + WebSocket 每次交互往返。而手机会把后台标签页挂起——
锁屏、切去回条消息、再切回来，WebSocket 已经断了。官方 issue 里有
[重连后白屏](https://github.com/zauberzeug/nicegui/issues/4253)的竞态，社区也反馈
`reconnect_timeout` 压不住那条「Connection lost. Trying to reconnect」。

**这一刀正好砍在命门上**：这个 app 的全部价值就是「掏出手机 3 秒记一笔」。
要是掏出来先等重连、正在输的金额还没了，那它就不如在 LINE 里发一句「我垫了 398」。

### 7.2 定稿

| 项 | 选择 | 理由 |
|---|---|---|
| 前端 | **Vue 3 + TS + Vite + Quasar** | Quasar 移动优先，手机 70% / 桌面 30% **一套代码都正经**；Vue3 你在 soroban、mercari_manage 跑过两轮 |
| PWA | **`vite-plugin-pwa`**（非 Quasar CLI） | service worker + manifest 自动生成。**选它而不是 `quasar build -m pwa`**：Quasar CLI 自带一整套构建系统且脚手架是交互式的；Vite + `@quasar/vite-plugin` 既拿到同一套 Quasar 组件，形态又和 soroban 的 Vite+Vue 一致。图标已生成在 `frontend/public/icons/` |
| 后端 | **FastAPI + SQLModel** | 纯 REST，**只返数据不返文案** |
| 数据库 | **SQLite (WAL)** | 4 个人的量，十年用不满 |
| 迁移 | **Alembic，但推迟到 schema 稳定**（D18） | 设计阶段 `create_all`；录真账之前必须切过去，否则改表就丢数据 |
| 金额 | `int` 日元，前后端都是 int | **禁 float**，JS 那边尤其要盯 |
| i18n | **vue-i18n**，只在前端一处 | 后端不碰文案，账单文本也在前端生成，自然跟随界面语言 |
| 草稿 | `localStorage`（D15） | IndexedDB 对这个量级是过度设计 |
| 测试 | pytest（算法/API）+ **Playwright 375px 视口** | soroban 已经跑过 Playwright，截图确认手机布局 |
| 部署 | **FastAPI 挂载 `dist/`，单端口单进程** | 「两个代码库」不等于「两个服务」，和 soroban 一个模式 |

> 代价说清楚：多一层 REST API 设计 + npm 构建，**工作量约 1.8 倍**。
> 换来的是锁屏回来页面还在、点击本地即时响应、真 PWA。手机占 70% 的前提下这笔划算。

### 7.3 ⚠️ 换栈带来的新问题：分摊算法要写两遍

前端要「改权重立刻看到每人金额」（不能每敲一下就往返服务器），
后端落库时必须自己再算一遍（**永远不信任客户端传来的金额**）。
于是同一个算法有两份实现，一旦不一致就会出现「预览 3,167、存进去 3,166」这种鬼故事。

**解法：共享一份测试 fixture。**

```
tests/fixtures/split_cases.json     ← 唯一事实来源
  [{ "amount": 9000, "weights": {...}, "adjustments": {...},
     "expected": {"a": 2167, "b": 3667, "c": 3166} }, ...]
        ↓                           ↓
  pytest 跑一遍              vitest 跑一遍
  （后端 Python 实现）        （前端 TS 实现）
```

两边跑同一组用例，谁偏了谁红。**新增分摊规则时先加 fixture，再改两边实现。**
另外保存成功后前端**用后端返回的 shares 覆盖本地预览值**，以后端为准。

### 7.4 手机优先的交互硬约束（D14）

这些不是「尽量」，是**验收标准**：

| 约束 | 怎么验 |
|---|---|
| 主操作按钮一律在屏幕**下半部**（拇指区），顶部只放不常点的 | 375px 截图人工确认 |
| **记一笔一屏完成**：金额（大字号，`inputmode="numeric"`，日元无小数直接唤数字键盘）→ 分类大色块网格一点即选 → 存 | ≤ 3 次点击 + 1 次输入 |
| 付款人/分摊**默认折叠**，常见场景不展开就能存 | 同上 |
| **分摊编辑器**：每人一行＝头像 + 权重 stepper（−/数字/＋）+ 实时金额；底部固定条常驻「合计 ¥X ／ 差额 ±¥Y」 | 固定金额模式下差额≠0 时红字且禁止保存 |
| 账目列表**左滑删除**、下拉刷新 | Playwright 手势测试 |
| **375px（iPhone SE）无横向滚动** | Playwright 断言 `scrollWidth <= clientWidth` |
| **锁屏 10 分钟回来：不重载、不丢正在输入的内容** | 手工测 + localStorage 草稿兜底 |
| 深色模式跟随系统 | 两种模式各截一张图 |

**桌面那 30%**：同一套代码走 Quasar 响应式断点，账单核对和「复制上月批量改数字」在宽屏下是**真表格**，不是被拉宽的手机。

### 7.5 中日双语（D4）

- 界面文案全部进 **vue-i18n** 的 `zh.json` / `ja.json`，组件里只写 `t('bill.you_owe')`
- **后端不碰文案**：API 只返数据和枚举 key，账单导出文本也在前端拼，自然跟随界面语言
- **用户数据不翻译**：分类名、模板名、备注是你自己录的，录什么显示什么
  （否则每个分类要存两个名字，纯找罪受）
- 语言跟人走：存 `member.lang`，登录后自动切；未登录看浏览器语言
- 金额/日期格式随语言变：中文 `¥150,400`、日语 `150,400円`
- **纪律**：M1 起 `.vue` 里不许出现裸中日文字符串，加一条 lint/测试扫描挡住

### 7.6 部署（D8）

M1/M2 先在 Mac 上本地跑通（后端 `uvicorn`，前端 `vite dev` 代理 `/api` → 8000，同 soroban）。
上线时 `quasar build -m pwa` → FastAPI 挂载 `dist/` → **一个端口一个进程**。

打包命令 `npm run build`（`vue-tsc --noEmit && vite build`），产物落在 `frontend/dist/pwa/`。

M3 再定 NAS / VPS，照 hiyori 的 `deploy.sh` 模式。外网访问届时三选一：
Tailscale（免费、数据不出门、室友要装 app）/ Cloudflare Tunnel（免费、自带 HTTPS、账本暴露公网）/ VPS（最省事、要钱）。
**代码层面不为此做任何特殊设计。**

> 注意 PWA 要装到主屏必须有 **HTTPS**（localhost 除外）。
> 所以真上线时 Tailscale（自带 HTTPS 域名）或 Cloudflare Tunnel 比裸 VPS 省事。
