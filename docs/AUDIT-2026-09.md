## A. ✅ 备份 —— 做了

原来的问题：`backup_path` 摆在面板上，说明写着「每日自动备份」，而**备份代码一行都没有**。
更糟的是库开着 WAL，实测主文件 4096 字节、`-wal` 3.9MB —— 按代码里原来那句
「备份就是拷这个 .db」做出来的备份，恢复出来是个**连打开都打不开的空库**。

现在：

* 每 24 小时一份（间隔和保留份数在设置里改，填 0 就不自动备），设置页上也有「立即备份」；
* 走 `VACUUM INTO`，产出**能单独打开的单文件完整库**（5 年规模实测 12ms，不阻塞写）；
* 先写 `.part`、当场验过（完整性 + 外键 + 逐表和源库对条数）才 `os.replace` 成正式名字 ——
  断电 / kill -9 / 盘满只会留下一个 `.part`，绝不会留下一个「看着像备份」的半截文件；
* 账本是空的时候**不备份也不轮转**（防「库被误删之后备份照跑，几天内把好备份全转掉」）；
* 设置页上那一行是**现场探出来的**（目录能不能写、盘够不够、最新那份真打开验过），
  不是读一条存下来的「上次成功」—— 存的那种会过期，而这个功能当初要治的就是那个毛病；
* `tools.restore` 一键恢复：先验备份、**比对表结构**、把现在的账本整个挪到 `data/replaced-*/`
  不删，最后才换上去。

恢复那条路实测过一个致命细节：只把 `.db` 拷回去而留着旧 `-wal`，
SQLite 会把旧 WAL 的页盖上来 —— 44 笔的备份读出来 127 笔，再读就是
`database disk image is malformed`。脚本把 `-wal`/`-shm` 一起处理掉，正是为了堵这一步。

**还剩两件要你掂量的**（都写在设置项的说明里了，不用回来改代码）：

1. 默认备到 `backend/backups/`，**和账本同一块盘** —— 防得住手滑和库坏，防不住盘坏。
   指到 iCloud / 外接盘更保险，但**那份文件是整本账的明文**（含密码哈希和三个人的头像），
   放云上等于「谁有那个账号谁就有整本账」。
2. 这个项目至今是 `create_all` 没有迁移（D18：录真账之前再切 Alembic）。
   在切过去之前，**每加一个字段，加之前做的那些备份就恢复不回来了**
   （恢复脚本会拦下来并说清楚，但那意味着那段时间的备份作废）。
   这是「Alembic 不该再往后拖」的一个新理由。

## B. ✅ 「已结清」判据 —— 按现状保留

> 上一轮你说「展开讨论现状（待办）」，这一节是那份讨论稿。

> 另有一条不是口径问题而是会凭空造债的 bug，那条早就修了，见 §B.4。

### B.1 改之前：窗口判据，必现的坑

旧判据除了下界「本张出账之后」，还砍了一刀上界「下一张出账之前」——
意思是「这张单子的钱要在下一张出账前到」。于是**只要拖过下一次出账再还钱就必踩**：

| 时刻 | 发生了什么 | S1 那张卡片 |
|---|---|---|
| 9/10 | A 垫 30,000 | — |
| 9/30 | 出 S1，方案 `B→A 10,000` / `C→A 10,000` | 两个橙按钮 |
| 10/31 | 出 S2，方案 `B→A 11,000` / `C→A 11,000`（累计，把没还的带进来了） | 两个橙按钮 |
| 11/2 | B 转给 A 10,000，在 S1 的卡片上按「确认已完成」 | **一个像素都没变** |

钱记上了，可这一页什么都不变（方案是冻结的，绿勾因为超了上界永远不亮）。
用户唯一能做的判断是「我刚才是不是没点上」，于是再按一次 —— 实测 B 从欠 10,000
变成倒被欠 9,000。而合租里「拖过一轮再还」是最常见的还款节奏。

### B.2 现在：判据是什么，边界在哪

去掉上界，改成「按这张单子的方案，该给的钱**后来**给够了没有」，
并且只累计方案里出现过的那几对。边界写清楚：

1. **绿灯是「至今为止的事实」，不再是「当期的事实」。** 同一张单子 10 月复制到 LINE
   写着「未结清」、12 月再复制可能写着「已结清」。
2. **按「谁给谁」匹配，不按用途匹配。** 转账没有「这笔是还哪张单子的」这个字段，
   所以 B 因为别的事转给 A 的钱一样会点亮 S1 的 `B→A` 行。
3. **同一笔钱会被多张单子各数一遍**（每张各自从自己的 cut 往后数）。这是设计使然，
   但它决定了绿灯**不能**被读成「这张单子的钱到账了」。
4. 认的是记账时刻不是业务日期；出账前记的转账进的是单子自身的「已预付」，两边不重不漏。

### B.3 现在这套的已知副作用：旧单子的绿灯会被后来的钱追认

B 为了还这一期的 11,000 转过去，上一期那笔 10,000 也会跟着亮。
债权本来就是全局累计的，说得通 —— 但「已结清」这个词现在同时指三件事：
「这张的方案执行完了」「这一对之间两清了」「全屋两清了」。三者互不等价。

### B.4 **已经修掉的那半**：旧单子上的按钮会凭空造债

这一条不是口径问题。**冻结的方案里那几对，后来可能再也不会有钱流过** ——
新开销把债权重新净额化之后，A 的钱是经 B 绕回来的，于是「C→A」那一行永远点不亮、
整张永远挂着「未结清」，而那个按钮还亮着。

实测（**两种结算模式都中**，不是只有「最少转账」那个模式）：

```
A 垫 30,000 → 出 S1（方案 B→A 10,000 / C→A 10,000）
C 垫 60,000 → 出 S2 → 照 S2 全转完
→ 全屋余额 {A:0, B:0, C:0}，已经两清
→ S1 仍显示「未结清」，按钮还在
→ 按一下：余额变成 {A:-10,000, B:+10,000, C:0}  ← 凭空造出来的债
```

修法是收掉按钮，不是改判据：**「确认已完成」只在草稿和最新那张上给**，
更早的只留绿勾，旁边写一句「这张的方案已经被后来的账单接手了」。
比「全屋两清时才隐藏」覆盖得全 —— 后者在「只还了一半」的情况下漏掉
（实测 B 只转一半时全屋没两清，按钮照样在，照样造债）。

### B.5 ✅ 已定：**保持现在这套**（新来的钱能填旧账）

你的原话：「新来的钱能填旧帐就行」。现在算的正是这个 —— `settlement_progress`
只卡下界（`created_at > 本张的 cut_at`）、没有上界，所以拖过几轮再还，
前面那几张的绿灯都会跟着亮。判据不动，这一节以下留作记录。

唯一要知道的边界：**配对是按「谁转给谁」认的**。后来的账单如果把钱换了条路走
（本来 C→A，新方案变成 C→B→A），旧单子上那一行就永远点不亮 —— 钱其实已经两清了，
但那张会一直写着「未结清」。这种情况屏幕上有话说（「这张的方案已经被后来的账单
接手了 —— 要结账去『未出账』那页」），而且旧单子上已经没有按钮，按不出假债来。
真要连这个也治，就得换成下面那套更严的判据。

## C. ✅ 改密码会断掉旧 session —— 做了

手机丢了 / 被人瞄到密码时，改密码是唯一的自救动作，而它原来不断任何已经发出去的
token（管 90 天）。

做法和审计建议的**不一样**：不给 `Member` 加 `token_epoch` 列。
因为实测发现**加一列会让老库直接打不开**（`create_all` 只建缺的表、不给已有表补列，
报 `no such column`），而现在还没到切 Alembic 那一步。
改成拿密码哈希过一道 HMAC 当版本号写进 token —— 密码一变指纹就变，
schema 一个字节都不用动。附带一个结构性好处：**版本号和密码是同一个东西，不可能对不上**
（加列的做法要靠人记得把 `+= 1` 放在对的分支里）。

界面上改完密码会自己用新密码重登一次，不会把自己也踢出去。

## D. ✅ 逐笔轮转的那 1 円 —— 预览不再假装知道

后端的轮转依据是 `entry.id`，而新记的一笔存下去之前没有 id —— 前端只能拿 0 算，
实测三个人分摊时**三次里有两次指错人**。改已有的账没这问题（id 已知，透传进去了）。

没有去改轮转依据（那等于改 SPEC，而且会让同一天记的几笔把 1 円都给同一个人）。
改成：**换个 seed 再算一遍，结果变了就说出来**——「除不尽的 1 円按逐笔轮转归谁，
存下去才定得下来」。这一项默认是「归付款人」，只有主动改成 rotate 才看得到这句话。

## G. ✅ 后端不再返界面文案 —— 做了

## 附：有歧义的名字（你判断要不要改）

明显写错的那条已经改了：`Statement.covers_from` 的字段说明写着「这张单子里最早

| 同一份备份恢复两次，第一次挪走的原账本被静默覆盖 | 「挪走不删」这张安全网正好在最需要它的时候消失 |
| 上期结转用两条独立聚合算 | 并发下算出「账本不平」，`GET /api/bill` 直接 500。实测：一边改已出账的账、一边看账单，6 秒里 3582 次读炸了 248 次；改成一条 UNION ALL 之后 3420 次读 0 次 |
| 两个人同时打开账单页 | 「和上期一样」的固定费各记一笔，当期房租凭空翻倍（面板一行只显示得下一笔，金额看着是对的、合计是两倍） |
| 回头删掉一笔**已出账**的固定费 | 本期的「和上期一样」整月静默关掉，一句提示都没有，出账时按 0 结 |

## 我替你定的三件事（可以推翻）

1. **全新部署进不去门** —— 库里一个成员都没有，而建成员要求先登录。
   没做「第一个人免鉴权」的自助注册（那扇门要么一直开着、要么靠「库里有没有人」
   开关，而这个判断在恢复备份、批量删人那几天都会出岔子），
   改成一行命令：`python -m tools.add_member go Go`，顺带能 `--reset` 重置密码。
   README 的「跑起来」已经换成它。
2. **垫付人搬走了 / 规则没算上新室友** —— 「和上期一样」原来照抄不误：
   前者记出来是「已经不住这儿的人又垫了一次房租」，账单反过来叫留下的人给他转账；
   后者让新室友分摊 ¥0，黑字入账、零提示。现在两种都**不记了**，
   走已有的「这几项这次没替你记」那条黄色提示，让人自己去定。
   另一条路是「悄悄换个垫付人 / 退回同权」—— 我选了响一声，因为这两件事都涉及钱的归属。
3. **记一笔之后刷新哪些缓存** —— 原来每记一笔都把「翻过的每一张历史账单」重算一遍
   （5 年的库上一张 70ms）。现在只有**改/删已出账的账**和**记一笔转账**才连历史一起刷，
   新记支出/收入只刷当期草稿。判据写在 `bills.ts` 的 `refreshCached` 上。

## 下一步的优化方向（goal 第 5 条）

按「现在值不值得做」排，前两条有实测数据撑着：

1. **`audit_log` 占了整个库的一半。** 5 年规模的临时库实测：`audit_log` 1.61MB /
   全库 3.18MB ＝ 50.8%，算上索引 59.3%。它存的是每次改动的完整前后快照。
   备份、恢复、`VACUUM INTO` 的成本全跟着它走。做法：只留最近 N 个月的明细，
   更早的压成一行摘要 —— 但**这是把可追溯性换成空间**，得你点头。
2. **账目页一次拉 500 笔、筛选和合计全在前端做。** 现在有截断提示兜着（`truncated`），
   三个人按种子数据的速率大概能撑五年。真撑不住那天要往服务端挪筛选和合计，
   不是现在。
3. **SQLite 的读快照。** pysqlite 不为 SELECT 开事务，所以一次请求里的几条 SELECT
   各看各的最新状态。上期结转那处已经并成一条 SQL（最要命的那个），
   剩下「先取账目、再取分摊」的那一条缝要撞上「另一个人正好在改同一笔」才会显形，
   概率低得多。真要根治是给每个请求开一个显式的读事务（`BEGIN`），
   代价是写请求可能撞上快照冲突 —— 三个人的规模不值得换。
4. **E2E 只覆盖主线。** 这一轮修的多数是「第二个人同时在操作」「断网回来」
   「翻旧账单」这类旁支，靠的是单测和实地复现脚本。要不要把几条旁支也钉进 E2E，
   取决于你之后改动这一块的频率。

## 附：第二轮记下的名字与结构（你判断要不要动）

| 在哪儿 | 观察 |
|---|---|
| `bills.ts` 的 `seq` / `written` / `generation` | 三道防「旧请求盖新数据」的闸，各挡各的：`seq` 挡同一个槽的旧那发、`written` 挡跨槽（`'current'` 和 `'st:N'` 写同一份缓存）、`generation` 挡出账那一刻在路上的整代。票号全局单调，所以 `written` 其实也盖得住 `seq` 那种情况 —— 留着 `seq` 是为了少一次「旧值闪一下再被纠正」。三个名字摆在一起要读注释才分得清，但合并会牺牲那个不闪 |
| `refreshCached(touched?)` | 参数名是「被动过的那一笔」，判据却是「要不要连历史账单一起刷」。要更直白的话可以改成显式的 `scope: 'draft' \| 'all'`，代价是判据从 store 挪到四个调用点，容易各写各的 |
| `_stale_for_today` / `_prune_rule` | 一个管「人多了」（拦下来报出去）、一个管「人少了」（剔掉照记）。名字看不出这层分工，靠 docstring 说清 |

# 第三轮：UI 交互（2026-09-22 晚）

这一轮的靶子是界面。两路并行：**结算语义专项对抗审计**（6 个角度 + 逐条反驳验证，
54→11 条确认）和 **UI 交互审计 + 三份独立视觉方向提案**（5 路审计在真机尺寸的
WebKit 里实地点，3 份方案各自读代码、看屏幕后给完整的 token 和逐屏改法）。

## 最要命的两条（都在界面上，都让人多掏钱）

**1. 屏幕在指挥人转一笔已经不用转的钱。**
后端一直算着「这一笔已经转过多少」（`settled_paid`），可这个数以前**只送进了
对话框的预填值** —— 屏幕上、复制进 LINE 的文本里，全是方案原额。于是：

- 已经还清的人，打开 App 看到的最显眼一行仍是「你要给 Zen ¥9,999」，他会再转一次
  （实测多付 ¥9,999）；
- 群里那份文本同样点名要他这笔钱，另外两个人也看不出他已经还了。

**2. 「确认已完成」按钮的开关判据是错的。**
原来按「这是不是最新那张单子」给按钮 —— 两头都错：

- 最新那张的方案**同样会在出账后作废**（有人没照方案走：现金、并单转、经第三人；
  或者下一期又记了账）。实测：全屋余额已经全是 0，按一下就凭空造出一万块债 ——
  正是更早那些单子上已经修掉的那件事，在最新那张上原样还在；
- 而更早那张上的钱**可能确确实实还欠着**，收掉按钮等于没地方记。

改法是**把「行」和「行动」分开**：每人行和转账方案仍然是出账那一刻的历史陈述，
而大字、进度、按钮一律看后端新给的 `live_transfers` / `live_closing`（此刻还欠不欠）。
于是按钮在「钱已经绕别的路还清」时自己就不在了，在「旧单子上的钱还欠着」时反倒能用。

## 这一轮还修了（UI 审计 20 条里的大部分）

|---|---|
| 固定费金额框点进去不全选 | 把 8,700 改成 8,900，输出来是 **89,087,000**，而这一屏「改完自动保存」，没有确认也没有撤销 |
| 分配条两个手柄能叠死 | 把某人推到 0 之后，他左边那条分界线**永远按不住了**（实测命中区 0px） |

| 全站次要灰字 2.85:1 | 账单上「谁垫了多少、上期结转多少」是全页最淡的字 |

## 视觉：做了什么

- **新建 `src/css/tokens.css`**：色阶（每个值都标着实测对比度）、字阶、圆角。
  顺手接管 Quasar 的灰阶工具类 —— 全站 56 处散在十来个组件里，一处一处换必然漏。
  配了一条守卫用例，直接从 tokens.css 读值算 WCAG，改坏当场红。
- **账单头部层级倒置修了**：原来最大的数字是「合计」（谁也不用去做什么），
  而真正要做的事「你要给 Zen ¥101,474」是第三行 17px 红字。现在拆成
  小标签 + 28px 的数字。
- **「每人」那块加了按人上色的发散条**：一条 6px 细杠贴在行底，中轴贯穿三行，
  左边要付右边要收，长度就是旁边已经印出来的那个数。**不占一个新像素**
  （在背景层），那 12 个灰数字一个没删 —— 但「谁欠得最多」从「读三行算一遍」
  变成一眼看形状。
- **分类格子给了自己颜色的淡底**。原来未选中是完全透明的，三个方向的评审和
  照着任务走一遍的那一路都在这儿卡住过 —— 屏幕上那就是三行说明文字。
- **分摊那一屏**：比例药丸补了个 ▾（原来像个填不进去的灰框）、「不参与」
  明写出来（那个手势原来零提示）、行高 48→52。

## 比例滑块（你点的第 4 条）

分摊面板顶上加了一条**可拖的分配条**：按人上色，按住两段之间那道杠推，
钱就在相邻两个人之间流动。

关键取舍：**它写的是「调整额」，不动「份数」**。份数（1:1:2，「谁算几个人」）
和调整额是这套分摊本来就有的两个概念，拖动只是给后者一个直接操作的入口 ——
于是份数那一列一个字不变，拖出来的差额明明白白落在「调整」那一格里，
看得见、能再手改、也能一键清零。合计永远等于金额（拖动只在相邻两人之间挪钱，
调整额之和恒为 0）。

## 我替你定的，你可以推翻

1. **旧单子上欠着的钱现在可以直接结** —— 按钮的判据换成「此刻还欠不欠」之后
   自然的结果。原来是「只有最新那张能结」。
2. **拖动条每段留 44px 下限，拖不到 0** —— 拖到 0 会让两个手柄叠死。
   「这笔他不参与」有专门入口（点头像），现在那个状态也明写出来了。
3. **分类格子铺淡底** —— 推翻了原来那条「不铺底」的注释。它没说错（灰底确实像
   一排空盒子），但「什么都不铺」的代价更大：看不出能点。淡底是第三条路。
4. **后端不再往库里写「8/30 出账」这种中文** —— 它会被写进 statement 表，
   日文界面上永远改不回来。现在留空，前端按日期用 i18n 渲染；
   库里的老名字认出来同样重渲，**不用写迁移**。
5. **顶部「支出/收入/转账」那块实心色块一个字没动。** 三份方案里有两份都想把它
   改轻，理由都成立（它是全屏最大的一片颜色）。但代码里那条注释写着
   「选错记账类型的代价比选错页签大得多」，而且有 E2E 钉着三段等宽、实心、三色不同 ——
   这是这个项目唯一一处明确为「防错」付过视觉代价的决定，我不在一次审美改版里推翻它。
