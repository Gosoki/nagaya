## A. 备份：现在等于没有

`backup_path` 这个设置项摆在面板上，说明写的是「每日自动备份的存放目录」，
而**备份代码一行都没有**。更糟的是：库开着 WAL，实测主文件 `nagaya.db` 只有
4096 字节、`nagaya.db-wal` 有 3.9MB —— 按代码里原来那句「备份就是拷这个 .db」
做出来的备份，恢复出来是个**零张表的空库**。

已经做了的（零风险那半）：把面板文案和 `models.py` 的注释改成实话，
README 也写明「手动拷整个 `data/` 目录」。

**要你定**：
1. 就停在「说实话」这一步，备份继续手动拷？
2. 还是现在就做？做法很短：`VACUUM INTO 'backups/nagaya-YYYYMMDD.db'` ——
   对 WAL 安全、不用停服、产出单文件完整库。挂一个 `POST /api/backup`
   端点 + cron/systemd timer 调它（不要在 FastAPI 进程里自己起后台线程）。
3. 顺带：`settlement_methods`（结算方式候选）同样零消费 —— 记转账那屏根本没有
   「用什么方式转的」这个字段。删掉，还是把那个字段补上？

## B. 「已结清」的含义变宽了

原来的判据是「**在这张单子自己的窗口内**（出账 → 下一张出账）转清了」。
那条路有个必现的坑：拖到下一张出账之后才还钱 → 当初那张永远点不亮 →
用户以为没点上 → 再转一次。实测走完这条路，B 从欠 10,000 变成倒被欠 1,000。

**已经改成**：「按这张单子的方案，该给的钱后来给够了没有」（去掉上界，
只累计 plan 里出现过的那几对）。代价是**旧单子的绿灯会被后来的钱追认**。

债权本来就是全局累计的，这个语义说得通。真要更严，得按「这一对之间的净债权
是否已清」算 —— 逐对债权要重算，比现在这套重。**要你定要不要更严。**

## C. 改了密码，旧 token 还能用满 90 天

手机丢了 / 被人看到密码 → 改密码是唯一的自救动作，而它现在**不断旧 session**。
改法不长：`Member` 加一列 `token_epoch`，`make_token` 写进 claim，
`current_member` 比一下不一致就 401，改密码时 +1。
代价：所有人当场被登出一次（包括改密码的本人）。**要你定做不做。**

## D. 「余数归谁 ＝ 逐笔轮转」时，新记那一笔的 1 円

后端的轮转依据是 `entry.id`，而新记的那笔在保存之前没有 id ——
前端预览只能用 0，于是除不尽的每一笔（三人分摊里大多数）预览和落库
指的不是同一个人。**编辑已有账目那半已经修好了**（把 id 透传下去）。

剩下「新建时那 1 円归谁」三条路，都要你定：
1. 换轮转依据（比如按日期序数），两边各自算得出来 —— 但 SPEC §4.1 白纸黑字
   写的是「entry 序号取模」，改依据等于改 SPEC，而且新旧两套依据会并存；
2. 预览那 1 円不显示归属（只说「除不尽，1 円以后端为准」）；
3. 不管 —— 这一项默认是 `payer`（余数归付款人），只有主动改成 rotate 才踩得到。

## E. 已经搬走的人，权限没有变小

实测：填了 `left_on` 的人照样能登录、记账、改别人的账、改全局设置、
甚至把自己的 `left_on` 清回来。

**但这不是 bug**（审计的反驳方推翻了它，我认同）：
- 产品里**根本没有「移出成员」这个动作**，前端一处都不写 `left_on`；
- `left_on` 是**分摊参与的日期窗口**，不是账号状态位 —— 和 `joined_on` 完全对称，
  「下个月才搬进来的新室友」现在也照样能登录；
- 真去 `current_member()` 里加 `if not is_active(): 401`，恰好会把那个新室友锁在门外；
- 而且 `bill.py` 的注释写得明白：「欠着钱走的必须一直挂在账单上直到结清」——
  他还得记那笔「我转给你 25,000」。

**真正要你定的是上游**：这屋里**没有授权模型**（`members.py` 的原话：
「这屋里三个人是互相信任的」），任何人都能改删任何人的账目、改全局设置。
做成员管理界面时要不要顺便引入「谁能做什么」？还是继续「三个人互相信任」？

> 相关：我一度把 `left_on`/`joined_on` 也做成了「只能改自己的」，**已经回退**。
> 理由同上：人搬走之后不会再开这个 app，只许本人改的话谁也标不掉他，
> 从此每笔账都照样算他一份 —— 比要防的问题更糟。
> 保留的只有 `name` 和 `password`（改掉别人的登录名＝把人锁在门外，没有自救手段）。

## F. ~~两张从来没用过的表~~ —— 已查明是计划中的坑（不删）

`Template` / `Bundle` / `entry.receipt_path` 看着像死代码，但 SPEC 里它们都在路线图上：

| | 在 SPEC 的哪 | 现状 |
|---|---|---|
| `Bundle` + `entry.bundle_id` | **M3**「光熱費套餐（电/煤/水/网一屏录入）」 | 表在、字段一路接到前端类型，但没有端点能建，`bundle_id` 恒为 null |
| `Template` | **M3**「模板（房租固定额）」 | 表在，一行读写都没有 |
| `entry.receipt_path` | **M4（可选）**「收据拍照」 | 字段在，`EntryOut` 都没带它 |

所以**审计把它们叫「死表」是看漏了 SPEC**，我没删 —— 这是你自己「路已留好」的groundwork。
已经做的是把这件事在 `models.py` 上标清楚（「M3 的坑，现在还没人写它」），
免得下一个人再追一遍。乱指 bundle_id 会 500 那条是真 bug，已经修了。

实测过删掉是安全的（万一你想删）：`create_all` 只建缺的表、不删多余的列，
用「删了 Bundle 的 models」打开老库，SELECT 和 INSERT 都正常，
残留的 `bundle_id` 列是 nullable，只是没人管它了。

## G. 后端还有 38 处硬编码中文错误文案

`schemas.py` 开头自己定的规矩是「后端只返数据和枚举 key，**不返界面文案**」，
而 `HTTPException` 那一路全是中文句子（`"账目不存在"`、`"只能改自己的密码"`…）。

给它们也配 code + 注册一个 `HTTPException` 处理器重整响应体。
**要你定值不值得**（低优先：现在的下场是「日文界面看到中文」，不是坏掉）。

## 附：有歧义的名字（你判断要不要改）

明显写错的那条已经改了：`Statement.covers_from` 的字段说明写着「这张单子里最早
一笔的日期」，而它存的是**上次出账那天** —— 差别不是文字游戏，「7 月那张从 7/2
开始」是错觉，7/1 只是没人花钱。

剩下三处是「读得懂但要想一下」，不改也能跑：

| 名字 | 问题 |
|---|---|
| `carried` | **同一个词指两件无关的事**：`bill.carried` ＝「上期结转」（余额滚过来的钱），`monthly.carried` ＝「按上期金额记上了」（和上期一样那个开关）。后端也一样：`carry_same_as_last` 和账单里的 `opening/carried` 同根不同义。界面文案本身不会让用户混（一个写「上期结转」一个写「按上期金额记上了」），是**给写代码的人埋的坑**。 |
| `MonthlyData.total` | 它是「本期固定费合计」，而 `Bill.total_expense` 是整张账单。放在一起看容易读成同一个量级的东西。叫 `monthly_total` 会更明确。 |
| 取数的六个词 | `load` / `reload` / `ensure` / `refresh` / `refreshCached` / `warm` 各有各的意思（`ensure` ＝ 缓存先上屏、`reload` ＝ 强制重取、`warm` ＝ 预热…），`bills.ts` 里都写了注释，但六个同义词摆在一个 store 上，第一次读要来回翻。 |
